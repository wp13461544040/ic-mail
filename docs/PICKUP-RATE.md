# 分层取件限流

本规则适用于 v0.2.0 之后的共享收件修复，替代共享模式的“每次完成后再冷却 2 秒”。取码响应的 JSON 结构保持不变；Apple 创建限额与本规则无关。

## 默认共享模式

- 同一个 root 的 Pool、Bearer、取件链接共用速率桶：容量 2，每 2 秒补 1，最多存 2 次。切换凭据或 `+tag` 不产生新桶。
- 开始一个合法取件请求扣 1 次；额度内允许同 root 多个读者共享同步，普通请求和 Pool 长等待不互斥。各自结束只释放自己的计数，单请求取消不终止共享收件。
- 请求执行、等待新码期间额度持续恢复。结束、失败、取消均不把恢复时间推到“现在再加 2 秒”。失败请求已消耗的额度不返还，避免错误重试打满上游。
- 拦截不扣额度、不重置时间、不占用新的 alias/主号名额。其他 root 使用各自额度。
- 上游保护独立：同主号共享同步、最多 1 个读取连接、实际启动最短 2 秒、全局 IMAP 并发有界、失败退避。允许一次快速刷新不表示重新登录 Apple。
- 共享 HTTP 入口取消每秒 100 次与每主号 64 个的限制。全站最多 512 个在途、入口总计最多 1024 个请求（含排队），排队预算 2 秒；Pool 长等待最多 384 个在途、总计最多 640 个（含排队），为普通读取预留执行和入口容量。
- 并发、队满、排队超时及 alias 状态表容量不足返回 `503 PICKUP_BUSY`，并附建议重试时间；并发本身不返回 429。429 用于同 root 刷新速率超限。容量上限约束 HTTP 等待资源，不增加 Apple 连接数。
- Pool 取码本地复验使用共享读锁，多个读者并行；轮换、释放与退役仍互斥复验。首次同步耗尽 `wait_seconds` 时做最终本地检查，正常返回新码或 `no_code`，不因等待预算用完直接产生同步故障。

关闭共享模式的旧路径可能逐次直连上游，因此仍保持单 alias 独占、完成后 2 秒冷却、全站 16 / 主号 2 个在途；容量忙返回 503，冷却与每秒 100 次入口速率限制仍返回 429。

## 典型时序

| 操作 | 结果 |
| --- | --- |
| 空闲后读取一次，再快速刷新一次 | 2 次都可准入，复用主号收件结果 |
| 同一时刻第三次请求 | 429，约 2 秒后恢复 1 次 |
| 1.8 秒时再次刷新 | 429，剩余约 200 ms；不重新开始 2 秒 |
| 2 秒时刷新 | 恢复 1 次准入 |
| 一个长等待期间普通读取 | 有速率额度时正常准入；不取消等待者 |
| 已等待 15 秒的请求结束后立刻再取 | 若无其他读者消耗，已有恢复额度，直接准入 |
| 同 root 再开第二个长等待 | 有刷新额度时共享同步；无额度时 429，按剩余时间重试 |
| 同主号 200 个不同 root 同时取件 | 不受旧 64 个在途或全站 100 次/秒限制，共享主号读取 |
| 全局容量暂满 | 有界排队；队满或排队超时返回 503，不返回并发 429 |

## 刷新限流与容量繁忙

刷新频率超限为 `429 RATE_LIMITED`，容量繁忙为 `503 PICKUP_BUSY`。两者均附 `Retry-After`、`X-Retry-After-Ms` 和兼容原因头 `X-RateLimit-Reason`：

| `X-RateLimit-Reason` | 含义 |
| --- | --- |
| `mailbox_rate` | 同 root 突发额度已用完 |
| `mailbox_inflight` | 旧非共享路径同 root 已在读取，503 |
| `mailbox_cooldown` | 旧非共享路径完成后的冷却 |
| `account_concurrency` | 旧非共享路径主号在途名额已满，503 |
| `global_concurrency` | 全局执行容量不足或排队超时，503 |
| `global_queue` | 全局入口受理容量已满，503 |
| `wait_queue` | 长等待入口受理容量已满，503；普通读取保留容量 |
| `wait_concurrency` | 等待长等待执行名额超时，503 |
| `global_rate` | 旧非共享路径全局每秒入口速率超限，429 |
| `mailbox_capacity` | 有界 alias 状态表已满，503 |

`Retry-After` 是剩余等待时间向上取整后的秒数；`X-Retry-After-Ms` 为毫秒值。对在途、等待或容量繁忙，返回的是建议复查间隔，不是已知完成时刻。采样日志记录 `limit_reason`、`retry_after_ms`，不记录凭据或邮件。

客户端优先采用一个 `wait_seconds` 请求，按总 deadline 处理 `no_code`、429、503，不把空结果当永久失败；不要同时启动多个同 root 长等待。轮询可保持 2 秒间隔，但无需在已经等待很久的请求结束后再固定睡 2 秒。普通读取仍自行鉴权、复验租约与凭据，增加额度不放宽项目/邮箱隔离。
